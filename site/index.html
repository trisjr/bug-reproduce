Reproducibility layer for Node.js

Production happened.
Now replay it.

Repro records the boundary of a failing execution — every value that crossed into your code from the outside — and seals it into a portable capsule. You replay that capsule on your machine, after the original environment is gone, and your application walks the same path with the same inputs.

Why observability is not the gap

Logs, traces, metrics and stack frames answer “what happened?” — brilliantly. They were never designed to answer the question that actually unblocks you: “can I make that same execution happen again?”

That is a different problem. Repro does not replace Sentry, Datadog, an APM, a logging platform, a testing framework or your CI. It adds a reproducibility layer on top of the diagnostics you already have.

And cloning production does not work

The environments never line up.

Production

  • Kubernetes, 20 API replicas
  • PostgreSQL cluster
  • Redis, Kafka
  • Live external APIs
  • Cloud infra, secrets, flags

Local

  • Docker, 1 API
  • Local PostgreSQL
  • Local Redis
  • Mock services
  • .env

Cloning that produces enormous complexity and still does not reproduce the bug — because the bug was never caused by the infrastructure. It was caused by the inputs that execution received.

How it works

Five stages, one boundary.

Repro intercepts your application in-process, seals what crossed the boundary, and hands you a capsule you can run anywhere. The stages below are the real pipeline, not a metaphor for it.

Capture

@repro/node · in production

The SDK tracks execution context with AsyncLocalStorage and monkey-patches the boundary: pg, http/https, the clock, and flag evaluation. Capture is failure-triggered and asynchronous, so a healthy request path pays nothing.

  • Bounded by design — a ring buffer caps a capsule at 100 interactions / 64 KB (SEC-008)
  • Redacted at capture time — before anything is written, not after
  • Zero external production dependencies — the SDK ships no third-party runtime code (SEC-037)

Seal

@repro/core · envelope encryption

The recorded boundary becomes a Repro Capsule: a POSIX ustar archive carrying a Manifest v1, the interaction log, and a runtime fingerprint. The payload is encrypted with AES-256-GCM under a data encryption key generated from a CSPRNG; the key itself lives at Key Custody, never inside the capsule.

  • Digest before parse — HMAC-SHA256 checked with timingSafeEqual before any JSON or tar is read (SEC-027)
  • Zip-Slip safe — path traversal and decompression bombs are rejected at read time (THREAT-009)
  • Memory zeroization — the DEK buffer is overwritten with 0x00 after use (SEC-038)

Pull

@repro/cli · on your machine

repro pull cap_1842 fetches the capsule into local storage and locks it down on arrival. Production data landing on a laptop is treated as the sensitive event it is.

  • POSIX permissions — 0600 on files, 0700 on directories (SEC-042)
  • Git Guard — refuses to write a capsule into a Git repository unless it is explicitly ignored (SEC-043)
  • Crypto-shredding — repro purge destroys the key at custody, rendering the capsule permanently unreadable (GDPR Art. 17)

Replay

@repro/replay · deterministic

The replay engine injects the original request into your local code and answers every outbound call from the capsule instead of the network. The clock is frozen at T0, so time-dependent branches take the branch they took in production.

  • Wire mocking adapters — a PostgreSQL query matcher, an outbound HTTP responder, a feature flag evaluator
  • Virtual clock — deterministic and frozen at T0 (ADR-010)
  • Layer 1 write defense — an AST SQL filter blocks mutating DML/DDL, an HTTP verb guard blocks non-idempotent verbs
  • Fail-closed — FallbackGuard enforces Rule E9: zero live network, zero live database, no silent fallback (ADR-005)

Diff

@repro/diff · verdict

A replay is only useful if you can trust it. The diff engine compares the recorded and replayed executions and returns a verdict — matched, or diverged with a reason.

  • Four canonical normalizers — SQL whitespace and casing, URL query ordering, recursive JSON sorting with float rounding, header filtering (ADR-006)
  • Two-tier equivalence — tier 1 byte equality, then a tier 2 semantic rubric
  • Six-step divergence attribution — when it diverges, you are told which boundary drifted and why
  • Terminal execution diff — a two-column side-by-side readout, with the first divergence marked

Architecture

Five packages, one workspace.

Repro V0.1 is an ESM-native npm workspaces monorepo. Each package owns one stage of the pipeline and depends only on the domain core.

@repro/core

Domain types & cryptography

Zod and JSON schemas, Manifest v1, AES-256-GCM authenticated envelope encryption, HMAC-SHA256 digest-before-parse SEC-027, memory zeroization SEC-038, the Key Custody REST client, and Zip-Slip safe POSIX ustar tar I/O THREAT-009.

@repro/node

In-process capture SDK

AsyncLocalStorage context tracking, monkey-patching interceptors for pg and http/https, format-preserving PII and PAN scrubbing with Luhn verification SEC-002 SEC-005, and a bounded ring buffer capped at 100 rows / 64 KB SEC-008. Zero external production dependencies SEC-037.

@repro/replay

Deterministic replay engine

Wire mocking adapters for PostgreSQL, outbound HTTP and feature flags; a deterministic virtual clock frozen at T0 ADR-010; a synthetic request injector; and Layer 1 write defense — L1AstSqlFilter, HttpVerbGuard, and a FallbackGuard that enforces Rule E9 fail-closed.

@repro/diff

Verification & diff engine

Four canonical normalizers ADR-006, two-tier equivalence combining byte equality with a semantic rubric Story-13, six-step divergence attribution Story-14, and a terminal diff UI that speaks the §20.16 contract language.

@repro/cli

Developer CLI

Six developer verbs — list, pull, inspect, replay, diff, verify — plus POSIX permission enforcement SEC-042, Git Guard SEC-043, and the operational commands purge (crypto-shredding, GDPR Art. 17) and keys rotate.

Security & privacy

Capturing production means capturing production data.

That is treated as a first-class design constraint, not a setting. Every guarantee below is implemented and covered by the test suite.

Zero-dependency SDK

@repro/node carries no external production dependencies, so the code you install into your production process has no third-party supply chain.

SEC-037

Redaction at capture time

authorization, cookie and x-api-key headers and sensitive fields such as password, secret and token are scrubbed before storage. Card numbers are format-preserved and Luhn-checked.

SEC-001SEC-002SEC-005

Envelope encryption

AES-256-GCM authenticated encryption with a data encryption key generated from a CSPRNG. The key never travels inside the capsule.

SEC-009…012ADR-012

Digest before parse

An HMAC-SHA256 digest is verified with timingSafeEqual before a single byte of JSON or tar is parsed — closing off Zip-Slip and decompression bombs at the door.

SEC-027THREAT-009

Crypto-shredding & zeroization

DEK memory is overwritten with 0x00 after use, and repro purge permanently deletes the key at Key Custody, which then answers 410 Gone / SHREDDED.

SEC-016SEC-038Story-08

Fail-closed write defense

L1AstSqlFilter blocks all mutating DML and DDL, HttpVerbGuard blocks non-idempotent verbs, and FallbackGuard enforces Rule E9 — a replay never reaches a live network or database.

ADR-005Story-12

Permissions & Git Guard

Capsule files are written 0600 and directories 0700. Pulling a capsule into a Git repository is blocked unless the path is explicitly ignored.

SEC-042SEC-043

Failure-triggered capture

Healthy traffic is never recorded. Capture is triggered by a failure, runs asynchronously off the request path, and is capped at 100 interactions / 64 KB — so the blast radius of any capsule is bounded by design.

ADR-008SEC-008

Self-hosted by default

The topology is private and self-hosted: capsules and keys stay inside your own infrastructure. No production data is sent to a vendor.

Quickstart

Two moves: instrument, then replay.

Requires Node.js 22 or newer.

In your application

Install the capture SDK and initialize it in your entry point.

$ npm install @repro/node
import repro from '@repro/node';

repro.init({
  appName: 'checkout-service',
  appVersion: '1.0.0',
  capture: {
    postgres: true,
    httpOutbound: true,
    clock: true,
    featureFlags: true,
  },
  redaction: {
    neverStoreHeaders: ['authorization', 'cookie', 'x-api-key'],
    maskPii: true,
    luhnValidation: true,
  },
  storage: {
    maxInteractions: 100,
    maxBytes: 64 * 1024,
  },
});

Wrap the handlers you care about, or let uncaught exceptions trigger capsule generation on their own.

app.post('/api/checkout', repro.wrapHandler(async (req, res) => {
  return await handleCheckout(req.body);
}));
On your machine

Six verbs take you from “a capsule exists” to “the fix holds”.

# Browse available capsules
repro list

# Fetch one locally — chmod 0600 + Git Guard
repro pull cap_1842

# See what was captured
repro inspect cap_1842

# Replay deterministically against local code
repro replay cap_1842 --port=3000

# Two-column execution diff
repro diff cap_1842

# Verify the fix on current code
repro verify cap_1842

# Crypto-shred keys at custody (GDPR Art. 17)
repro purge --before=2026-08-01 --hard
The verbs
CommandWhat it does
repro listLists capsules available to you.
repro pullDownloads a capsule and locks down its permissions.
repro inspectPrints the manifest and the captured boundary, redactions included.
repro replayRuns your local code against the capsule with a frozen clock.
repro diffShows recorded against replayed, side by side, first divergence marked.
repro verifyAnswers one question: does the bug still reproduce on this code?
repro purgeDestroys capsule keys at custody. Not reversible.
repro keys rotateRotates key material at Key Custody.
